## 1. Before the new code first runs on the PC (in this order)

1. **Know what you have.** `git log --oneline -1`, and `git status`: the only change you expect is
   the PC's own `uv.lock` rewrite (step 6). Anything else, commit or put it aside first.
2. **Stop the gateway and the backup timer:** `systemctl --user stop hermes-gateway-stash` (unit and
   commands from ADR 0005) and, if it is installed, `systemctl --user stop stash-backup.timer`.
   Nothing should write to the database while you copy it.
3. **Back up the database before any new code opens it.** Every stash command applies the
   migrations when it opens the store, `backup`, `doctor` and `list` included. Checked on the Mac
   with a fake schema-1 database: the new `stash backup` migrated the live file first, so its copy
   was already at schema 4. So take the copy with the *old* checkout, before step 5:
   `.venv/bin/stash backup --to ~/stash-pre-plan7 --config ~/.config/stash/stash.toml` (it creates
   the directory), or copy the files by hand,
   `mkdir -p ~/stash-pre-plan7 && cp ~/.local/share/stash/stash.db* ~/stash-pre-plan7/` (that glob
   also takes `-wal` and `-shm` if they exist) **(unverified)**. The data directory is `data_dir`
   in `stash.toml`; when that is not set, `$XDG_DATA_HOME/stash`, else `~/.local/share/stash`.
   Keep the copy out of the NAS backup directory and out of any directory a later `stash backup`
   writes to: the writer replaces a same-day `stash-YYYYMMDD.db` and prunes old ones.
   - Rollback is this copy. An older checkout refuses a newer database
     (`database schema version 4 is newer than supported 1`; `pc-m0` has the same check). Stop
     `hermes-gateway-stash` and `stash-backup.timer` first (either one reopens the database), check
     out the old commit, put the copy back as `stash.db` in the data directory, and delete
     `stash.db-wal` and `stash.db-shm` beside it **(unverified)**.
   - If the database holds only the spike's fake messages the owner may skip the backup.
4. **Remove `[library]` from `~/.config/stash/stash.toml`** if it is there:
   `grep -n '^\[library\]' ~/.config/stash/stash.toml`. The PC very likely never had it: `serve`
   landed 2026-11-07, after the last PC commit, and the example had the table commented out. If the
   PC did set `serve` up, follow the teardown note at the end of `docs/deploy/wsl-setup.md`
   (disable `stash-serve.service`, delete `serve.env`, remove both firewall rules, display name
   "stash library").
5. **Get the code.**
   - Which commit: `main`. Never push a branch the owner has not merged as `pc-m0`: the Mac merges
     `pc-m0` into `main` whenever `git log --oneline main..pc-m0` is not empty (`CLAUDE.md`, "PC
     updates"), so that would merge it without the owner's decision.
   - How: the PC was cloned from `stash.bundle` and its `origin` is the Mac's repo over SSH (setup
     findings, 2026-11-03); the spec plans a private GitHub remote ("always ask before pushing").
     The repo does not say which route is in use now. Either `git fetch origin` while the Mac is
     reachable, or a fresh bundle: `git bundle create stash.bundle main` on the Mac, copy it over,
     then `git fetch stash.bundle 'refs/heads/*:refs/remotes/mac/*'` (checked on the Mac with a
     throwaway repo: it creates one `refs/remotes/mac/<branch>` for each branch in the bundle).
   - Then on `pc-m0`: `git merge --ff-only mac/main` (`origin/main` after a plain fetch). `pc-m0` is
     an ancestor of `main`, so it fast-forwards unless the PC has committed since e698190. Findings
     commits go on `pc-m0`, on top of `main`.
   - Before switching or merging, drop the local lock rewrite: `git checkout -- uv.lock` (step 6
     redoes it).
6. **Lock file.** The committed `uv.lock` pins `pypi.apple.com`. The repo sets no index; the Mac's
   shell exports `UV_DEFAULT_INDEX` and `UV_INDEX_URL` for its mirror, and the URL does not resolve
   on the PC. After the merge run `uv lock --default-index https://pypi.org/simple` **(unverified
   for this lock; on 2026-11-03 the PC rewrote its lock by hand)**. Never commit the PC's lock.
   Dependencies changed since `pc-m0` by one dev dependency (`pytest-cov`) only.
7. **Install and gate:** `make install`, then a plain `make check`. The criterion is exit 0. The
   Mac counts at d107278 are 4,542 default tests and 111 integration passed, 1 skipped; with
   Tesseract 5.3.4 and the `ocr` extra present the skipped test should run, so expect 112 passed
   **(unverified)**. `pc-m0` had 3,036 and 60, so the numbers are not comparable.
8. **Doctor:** `STASH_CONFIG=~/.config/stash/stash.toml .venv/bin/stash doctor`, or
   `stash doctor --config PATH` (`--config` goes after the subcommand). This is the moment the
   real database goes from schema 1 to 4. Expect the config, the database, the AI providers, the
   GPU reading, the optional tools and the last backup (< 48 h); no library line.
9. **Backup unit**, only if the PC installed it from an earlier copy (the NAS mount was not done on
   2026-11-04): `cp deploy/systemd/stash-backup.{service,timer} ~/.config/systemd/user/`,
   `systemctl --user daemon-reload`, then `systemctl --user cat stash-backup.service` shows
   `ExecStart=%h/projects/stash/…` and `systemctl --user start stash-backup.service` writes
   `stash-YYYYMMDD.db` (the check in `wsl-setup.md` section 9).
10. **Start:** `systemctl --user start hermes-gateway-stash`, then
    `journalctl --user -u hermes-gateway-stash -n 80`. Look for: no config error at plugin load;
    one ticker start; no `no owner chat: reminders are off` warning (the ticker sends to the first
    id in `TELEGRAM_ALLOWED_USERS`, or `plugins.entries.stash.settings.owner_chat_id`); no
    `OutboxUnavailable`. The first tick on an existing database sends nothing (it seeds the
    ledger). Restart again after any `hermes -p stash plugins enable/disable` (ADR 0005).
    The hardening drop-in binds `~/.hermes` and `~/.local/share/stash` read-write;
    `library/latest.html` lands in the second, so the drop-in needs no change (read from the
    drop-in; the live write is row #27).

## 4. Quirks that are not bugs

- A **pending capture is not an item**: a message saved while the AI is down does not show in
  `stash list`. `/stash_retry` files it (`/retry` is a Hermes built-in).
- The **first tick** on an existing database sends nothing; it seeds the ledger. Changing
  `followup_time` re-asks the unanswered follow-ups of the last 14 days once; changing
  `reminder_time` or `digest_time` can repeat that day's sends once.
- Reminders are **late while the PC is off**, and Telegram keeps undelivered updates for about 24
  h, so shares made during a longer shutdown are lost (spec). A key-date reminder for a day the PC
  was off all day is not sent.
- The **cron fallback is off by default.** Do not run it together with the ticker on purpose.
- `[llm.thinking]` defaults send nothing. Set `filing = "off"` only after #19.
- Link filing took 62–82 s and plain filing 25–46 s with thinking on (ADR 0001, ADR 0004).
- The Hermes launcher warnings listed in ADR 0005 ("terminal policy unavailable", no backup into
  `~/.hermes/backups`) are expected.
